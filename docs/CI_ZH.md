# 持续集成

[English](CI.md)

本仓库的全部示例编译都由 GitHub Actions 执行。本地静态策略测试可用于开发，
但只有针对拉取请求已提交头部版本的工作流运行才是构建证据。

## 工作流

| 工作流 | 范围 | 精确矩阵 |
| --- | --- | --- |
| `esp-idf-examples.yml` | 9 个第一方 ESP-IDF 工程 | ESP-IDF v5.5.5 和 v6.0.2 |
| `arduino-examples.yml` | 9 个第一方 Arduino 草图 | Arduino-ESP32 3.3.11 |
| `repository-policy.yml` | 仓库策略与静态测试 | Python 标准库检查 |

每个拉取请求和每次推送到 `main` 都会进入工作流。廉价的发现任务会先对完整的
基准到头部差异进行分类，并识别重命名，然后才创建矩阵：

- 第一方示例修改只选择受影响的示例；
- 共享组件、库、构建脚本或框架工作流修改会选择对应框架的全部示例；
- 纯文档和保留固件修改不会选择示例构建；
- 删除或重命名示例路径会选择对应框架剩余的全部示例；
- 变更范围为空、不完整或未知时会关闭流程并失败，不会静默报告未经验证的结果。

每个框架工作流都有始终运行的结果任务。无论矩阵已运行、按策略跳过，还是发现
阶段失败，分支保护都能使用一个稳定检查。手动触发接受 `changed`、`all` 或一个
当前示例目录名。

## 仓库策略

策略工作流运行单元测试并检查：

- 第一方英文/简体中文 Markdown 配对及双向链接；
- 本地链接、锚点、首页结构和公开文本隐私；
- 纯文档范围和可识别重命名的构建路由；
- 仓库清单与示例发现预期；
- 通过 `git diff --check` 检查尾随空格和补丁格式。

嵌入的上游快照会被明确分类，不会为满足第一方文档样式而改写。

## 产物

成功的矩阵任务会上传 ZIP 文件，其中包含：

- `write_flash` 所需的全部二进制文件；
- `manifest.json` 中规范化的烧录偏移；
- 精确的框架版本和源码提交；
- `flash.sh` 与 `flash.bat` 辅助脚本；
- 适用时可移植的 ESP-IDF `flasher_args.json`。

打包会拒绝超出所选构建目录的路径、歧义二进制匹配、重复的规范化烧录偏移或
目标文件名，以及无法同时安全写入两种辅助脚本的文件名。实际烧录仍需要兼容的
Python 环境、`esptool.py` 和连接正确的设备。

## 版本策略

工作流用精确稳定版本确保可复现。版本更新应在聚焦的拉取请求中完成，并先检查
官方发布说明和迁移指南。不得把不断变化的 `latest` 标签解释为已验证，也不得在
该精确版本对应的已提交矩阵变绿前宣称支持。
